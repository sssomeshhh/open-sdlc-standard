# 9. Build and supply chain

- **ID prefix:** BLD
- **Status:** draft, 2026-10-31

## Purpose

This area protects against shipping something other than what the team reviewed and tested: artifacts built by hand from
unknown sources, dependencies that change underneath a build, components with unknown licences or known flaws, and
artifacts that cannot be traced back to their source or fetched again when needed. It matters because every running
system is only as trustworthy as the chain that produced it, and an auditor needs to be able to answer "what exactly is
running, where did it come from, and what is inside it".

## Scope

Covers: the automated build, dependency declaration, locking and pinning, dependency updates, reproducibility, licence
compliance, SBOM, artifact integrity and provenance, container base images and registry admission, the artifact registry
and its retention, and the build toolchain itself.

Leaves to other areas:
- Choosing and approving dependencies (build-vs-buy, dependency policy) and vendored code: see Area 2.
- What vulnerability, dependency and secret scanning has to find, and why: see Area 5. Running scans as blocking gates: see Area 8.
- Generated binaries and other files that are not to be tracked in the repository: see Area 7.
- Secrets policy: see Area 5. Secrets store and runtime configuration: see Area 10.
- Release identifiers, versioning, deployment from the registry (REL-2) and rollback: see Area 11.
- Least-privilege pipeline credentials and tokens: see CI-10 (Area 8).

## Requirements

### BLD-1 · MUST · Automated build from version control
Every artifact deployed to a shared environment MUST be produced by an automated build whose definition is in version
control and which runs on a build service from a commit in the shared repository, never built by hand on a workstation.
- **Gate:** G2
- **Evidence:** build definition files in the repository (CI workflow, build script, container build file); deploy records
  show each deployed artifact came from a named CI run of a named commit on the shared repository.
- **Basis:** [SLSA-BT], [AWS-OPS05-04], [SRE-RE].

### BLD-2 · MUST · Dependencies declared and locked
All direct dependencies MUST be declared in a manifest, with the full resolved set (including transitive dependencies)
locked in a committed lockfile that the build installs from in locked ("frozen") mode, so a build at the same commit
resolves the same versions.
- **Gate:** G1
- **Evidence:** manifest and lockfile in the repository; the CI install step uses the locked mode and fails when the
  lockfile is out of date with the manifest.
- **Basis:** [12F-2], [RB], [SRE-RE].

### BLD-3 · SHOULD · Pin unlocked build inputs by digest
Build inputs not covered by a lockfile (container base images, CI actions or plugins, downloaded tools) SHOULD be pinned
to an immutable reference (digest or commit hash), not a mutable tag or version range.
- **Gate:** G2
- **Evidence:** base images referenced by digest; CI actions referenced by commit hash; an automated pinning check (for
  example the OpenSSF Scorecard "Pinned-Dependencies" check) passes or lists only exceptions recorded in the tailoring record.
- **Basis:** [SCORECARD].

### BLD-4 · SHOULD · Hermetic, reproducible builds
Builds SHOULD be hermetic (independent of whatever is installed on the build machine) and aim to be reproducible: the same
source, build environment and instructions produce the same artifact, with known sources of non-determinism (timestamps,
file paths, ordering) controlled or listed with a justification for each.
- **Gate:** G2
- **Evidence:** documented build environment (pinned build image and tool versions); a rebuild of a past release that
  compares equal by hash, or a recorded list of the known differences, each with its justification.
- **Basis:** [RB], [SRE-RE].

### BLD-5 · MUST · Automated dependency updates, triaged on time
An automated dependency-update mechanism MUST be enabled for every dependency ecosystem in the repository, and its update
proposals triaged (merged, scheduled or declined with a reason) within a time limit the project defines.
- **Gate:** G1
- **Evidence:** update-tool configuration (for example Dependabot or Renovate) covering each manifest; the documented
  triage limit; age of open update proposals is within that limit.
- **Basis:** [SCORECARD]. Level: author's judgement (sources support SHOULD).

### BLD-6 · MUST · Licence compliance
The licences of all shipped dependencies MUST be identified automatically and checked against a written licence policy
(allowed, needs review, not allowed), and the obligations of the licences used (for example attribution notices or source
offers) met in what is shipped.
- **Gate:** G2
- **Evidence:** licence report generated by the build; the policy file; a third-party notices file in or with the artifact;
  review records for any "needs review" licences.
- **Basis:** [OPENCHAIN], [SPDX]. The content of the allow/deny list: author's judgement (no primary source found; the
  OpenChain programme defines a process, not a list). "Identified automatically": author's judgement (the cited sources
  do not require automation).

### BLD-7 · SHOULD · SBOM for every release
A machine-readable software bill of materials (SBOM) in a standard format (SPDX or CycloneDX) SHOULD be generated for every
release, regenerated whenever the release is rebuilt, kept with the release, and cover at least the NTIA minimum data fields.
- **Gate:** G2 · **Trigger:** each release
- **Evidence:** an SBOM file attached to each release or image; it contains supplier name, component name, version, other
  unique identifiers, dependency relationship, SBOM author and timestamp.
- **Basis:** [NTIA], [SSDF] (PS.3.2), [SPDX], [CDX], [CISA-SBOM], [SCORECARD].

### BLD-8 · SHOULD · Build provenance
The build SHOULD generate provenance for each release artifact that identifies the artifact by cryptographic digest and
records how it was produced (source commit, build platform, build definition, inputs), and publish that provenance
with the artifact (SLSA Build L1; L2 when a hosted build platform generates and signs the provenance).
- **Gate:** G2 · **Trigger:** each release
- **Evidence:** provenance or attestation files stored next to each artifact in the registry; their digests match the
  artifacts.
- **Basis:** [SLSA-REQ], [SSDF] (PS.3.2).

### BLD-9 · SHOULD · Signed artifacts when distributed beyond the team
Artifacts consumed outside the producing team (other teams, customers, the public) SHOULD be signed, and the consuming
deployment or installation verifies the signature or digest before use.
- **Gate:** G2 · **Condition:** when artifacts are first consumed outside the producing team · **Trigger:** each artifact released to consumers outside the team
- **Evidence:** signatures next to artifacts; the deploy or install step verifies the signature or digest and fails on
  mismatch.
- **Basis:** [SSDF] (PS.2.1), [SCORECARD]. The condition (distribution beyond the team): author's judgement.

### BLD-10 · MAY · Hardened build platform (SLSA Build Level 3)
The project MAY build on a hardened build platform that isolates build runs and keeps signing
material out of reach of user-defined build steps.
- **Gate:** G2 · **Condition:** when the supply-chain risk becomes high (wide distribution outside the organisation, or a contractual or regulatory requirement)
- **Evidence:** SLSA Build L3 provenance issued by the build platform; platform documentation showing run isolation.
- **Basis:** [SLSA-BT]. Condition: author's judgement.

### BLD-11 · MUST · Controlled artifact registry
Release artifacts MUST be stored in an artifact registry (package or container registry) where write access is restricted
to the build pipeline and named maintainers. Deployments pulling from the registry: REL-2.
- **Gate:** G2
- **Evidence:** registry configuration and permissions showing who and what can push; the release artifacts listed in the
  registry.
- **Basis:** [SSDF] (PS.1.1).

### BLD-12 · MUST · Artifact retention policy
A written retention policy MUST keep, for every release currently deployed and at least the previous release of each
environment, the artifact and its integrity and provenance data, and define when older artifacts are removed.
- **Gate:** G2
- **Evidence:** retention or lifecycle rules in the registry configuration; the exact artifact of any deployed or
  immediately previous release can be fetched by its identifier.
- **Basis:** [SSDF] (PS.3.1). The minimum retention ("deployed plus previous"): author's judgement (no primary source gives
  a retention period).

### BLD-13 · MUST · No secrets in artifacts
Build artifacts and container images MUST NOT contain secrets (in files, image layers, build arguments or environment
defaults); secrets are supplied at run time from the secrets store (see Area 10).
- **Gate:** G2
- **Evidence:** secret scan of built images and packages is clean; build arguments reviewed and contain no credentials.
- **Basis:** [SP800-190].

### BLD-14 · SHOULD · Approved base images
Projects that ship container images SHOULD build them only from a documented set of approved base images and registries,
and rebuild them at an interval the project sets so base-image patches are picked up.
- **Gate:** G2
- **Evidence:** base-image policy listing approved images and registries and the rebuild interval; build files use only
  those; rebuild records no further apart than that interval.
- **Basis:** [SP800-190]. Rebuild schedule: author's judgement (no primary source found).

### BLD-15 · SHOULD · Scan before an image enters the registry
The pipeline SHOULD push a container image to the release registry only after it has passed the vulnerability scan and
policy checks the project runs under CI-5.
- **Gate:** G2
- **Evidence:** pipeline order shows scan before push; registry contains no image without a matching scan report.
- **Basis:** [SP800-190].

### BLD-16 · SHOULD · Build toolchain under change control
The build toolchain and CI system (compilers, build tools, CI runners) SHOULD be updated at an interval the project sets
and changed only through reviewed changes. Least-privilege pipeline credentials: CI-10.
- **Gate:** G1
- **Evidence:** pinned toolchain versions; the documented update interval and an update history within it; review records
  for pipeline changes.
- **Basis:** [SSDF] (PW.6.1), [SLSA-REQ].

## Failure modes

- Artifacts built on a developer laptop or by hand, so nobody can say which commit is running, or a release is built from a
  commit that never reached the shared repository ([SLSA-BT], [AWS-OPS05-04]).
- Dependencies declared with open ranges and no lockfile, or a lockfile the CI install ignores, so a rebuild of the "same"
  version pulls different code ([12F-2], [RB]).
- Base images and CI actions referenced by mutable tags, so the build changes without any commit ([SCORECARD]).
- A dependency-update tool is enabled but its proposals are never merged, so dependencies age regardless ([SCORECARD]).
- Secrets passed as build arguments and baked into image layers ([SP800-190]).
- No retention rule: the artifact of the release in production can no longer be fetched for rollback or investigation
  ([SSDF] PS.3.1).
